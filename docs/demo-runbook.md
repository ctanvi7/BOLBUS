# BOLBUS hackathon demonstration

## What the demo is

BOLBUS runs as a local ETM simulator for a fictional training corridor (`DEMO-01`: Central, Market, College, Hospital, Lake). Every displayed fare and concession rule is synthetic training data. Approved records are simulated receipts stored locally in SQLite; they are not valid travel tickets. No BMTC data, fare source, ETM, payment system or printer is connected.

The conductor explicitly checks payment or concession eligibility/documents and approves each ticket. Speech only prepares editable fields. Fare checks and ticket state transitions stay on the backend.

## Start locally

Follow the Python 3.12 and Node setup in the root README. From the repository root, run these in separate terminals:

```powershell
cd backend
..\.venv\Scripts\python.exe -m uvicorn app.main:app --reload --host 127.0.0.1 --port 8000
```

```powershell
npm run dev --prefix frontend
```

Open `http://127.0.0.1:5173`. Keep both terminals running. The app's status indicator reports backend connectivity. A server restart preserves requests in `backend/bolbus.db`.

For speech, open `backend/.env`. `SPEECH_MODE=fixture` enables clearly labeled developer samples; these are not Gnani responses. `SPEECH_MODE=gnani` plus a server-side `GNANI_API_KEY` enables calls through the documented adapter. The live provider has not been verified against real credentials in this repository. If no key is configured, use the manual-text parser; do not describe typed text or fixtures as live recognition.

## Three-minute stage script

### 0:00–0:25 — Set the boundary

Show the DEMO DEVICE banner and active DEMO-01 route. Say: “This is a conductor workflow simulator. The stops, fares and concession policies are synthetic; there is no BMTC or ETM connection. The conductor retains the final checks and approval.”

### 0:25–0:55 — Prepare a manual ticket

On Home, select Central as boarding, Lake as destination, quantity 2 and Standard demo. Continue to review and validate. Point out the backend-calculated synthetic amount and fare-unavailable blocking behavior if you have a route without a matching fare rule. Save payment confirmation, enter a conductor name, explicitly approve, then show the simulated receipt.

### 0:55–1:35 — Use voice/text and clarification

Open Voice entry. First point out the visible speech status: Gnani configured, development fixture, or live speech unavailable. If live Gnani is configured, press Record, grant microphone permission and stop recording; otherwise type `Two standard tickets to Lake` and run Extract. State clearly that typed input demonstrates deterministic extraction, not speech recognition. Review the original transcript and editable fields. Try an unknown destination such as `Two standard tickets to Lakkee`; explicitly choose a suggested stop or select a destination. Save the batch to the pending queue. No request is approved by extraction or preparation.

### 1:35–2:05 — Show batching and interruption recovery

Use a phrase such as `Two standard tickets to Market, one standard ticket to Lake`, then save the separate requests as a batch. Return to Pending requests, open Saved batches, and show that each item can be reviewed, corrected, prepared, resumed and cancelled independently. Refresh the browser or navigate away and return to demonstrate saved server data plus local unsaved-field recovery. Point out that approval remains per-ticket.

### 2:05–2:35 — Demonstrate concession checks and ledger

Prepare one `Shakti-style DEMO` request. Show that voice does not select a concession for the passenger; the conductor must select the configured demo category and confirm eligibility and document checks. No document numbers or photos are collected. Explicitly approve it and show its synthetic receipt in the Trip ledger.

### 2:35–3:00 — Compare equivalent tasks

Open Compare demo. Choose or retain one matched scenario and complete Mode A and Mode B. Complete validation, payment/concession check and explicit conductor approval for both. Read the observed tap count, wall-clock time, corrections and unfinished count from this browser's round. Say that values are generated by these local attempts and are prototype measurements, not deployment benchmarks. For Mode B with typed input, disclose that recognition was not measured.

## Comparison measurement rules

- The selected scenario is locked for both attempts in the round.
- Each mode creates and approves a separate real backend simulated ticket against the same configured route/fare engine.
- Tap count measures pointer/button activations inside the comparison page, including mode start and explicit approval. It does not include keyboard keystrokes or navigation before entering the page.
- A correction is a changed populated field after its initial value has been committed (field blur). It is not a speech-recognition accuracy metric.
- Completion time is wall-clock time from starting an attempt until approval. If the conductor leaves and returns, that interruption remains in elapsed time.
- “Unfinished” is 1 when the conductor explicitly marks an attempt unfinished; an active attempt is retained for recovery and is not silently counted as abandoned.
- Results are browser-local and round-local. No seed/benchmark values are included. Clearing results starts a new round; it does not delete the simulated tickets from the ledger.

## Preflight checklist

- Confirm both local servers start and the status says Device ready.
- Confirm the demo banner and synthetic fare disclosure are visible.
- Check voice status before narrating speech; only claim live transcription if the Gnani server key is configured and the API call succeeds.
- Reset an old demo database only if its records are disposable; stop the backend first, back up the file, then remove `backend/bolbus.db`.
- On stage, use localhost only. The API has no authentication and must not be exposed on a public network.

## Unimplemented / unverified

There is no official fare or concession ingestion, payment settlement, ticket printing, production ETM integration, authentication/identity, general-purpose language understanding or complete offline synchronization. Live Gnani transcription requires valid credentials and a network connection; without those, use the clearly identified typed parser path. Real-device microphone behavior, noisy-bus accuracy and BMTC field usability have not been verified.
